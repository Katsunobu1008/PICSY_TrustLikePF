# ゾクゾク（ZOKUZOKU）｜UX設計・プロトタイプ実装仕様 v1.0
**コンセプト：好きがゾクゾクと。** 2026-10-22 / 構想検証用

## 0. 最初に固める設計判断
ゾクゾクは「AI画像生成ツール」ではなく、**自分でも明確に言えない『欲しい』を、生成・比較・引用・改良・発見を通じて探索し、実際の需要とつなぐ共創型商品開発サービス**である。UXの評価は生成枚数ではなく、*新しい好みの発見・役立つ改良・購入意思・商品化の事業性* に置く。将来のPICSYは創作の系譜と取引の評価関係を重ねる。初期は円建て・模擬予約のみ。

### 主要ユーザーと「やりたいこと」（JTBD）
| ロール | 状況・トリガー | 解決したいジョブ | 成功したと感じる瞬間 |
|---|---|---|---|
| A：既存グッズに満足できない高関与ファン | 公式グッズを見たがデザインに違和感 | 普段使いできる推しグッズを見つけたい | 「そう、これが欲しかった」と思い予約する |
| B：自分の好みを探索したい人 | 検索する言葉もまだない | 思いがけない表現に出会いたい | 新しい好みに気づく |
| C：創作・二次創作好き | アイデアはあるが描けない | 他人の案を発展させ、共有したい | 自作が引用・改良される |
| D：見る・選ぶ・応援したい人 | 生成する気分ではない | 作品を比較し、欲しい商品を見つけたい | 支持が商品化に影響する |
| E：商品企画担当者 | 企画の売れる根拠が薄い | 未充足需要と価格感度を理解したい | 製造判断に使える根拠が揃う |

## 1. UX設計に必要な要素：全体チェックリスト（24領域）
| 領域 | 検討すべき判断 | 受け入れ基準・証拠 |
|---|---|---|
| 01 問題定義 | 解くのは「生成できない」か「本当に欲しい商品がない」か | 実際の購入見送り体験を語れる |
| 02 JTBD | 利用目的のない探索を含めるか | 明確な目的がなくても初回体験に入れる |
| 03 セグメント | 作る・見る・改良・買うを別行動として扱う | 非創作者も使える |
| 04 提供価値 | 初回15秒で何ができるかわかるか | 言葉が短く具体的 |
| 05 情報構造 | 見つける／つくる／マイ作品／インサイトを分離 | 目的地まで2クリック程度 |
| 06 エントリーポイント | 店舗QR、SNS、IP公式、直接流入 | 流入元別の体験と権利を維持 |
| 07 オンボーディング | 最初からログイン・長文プロンプトを強制しない | ゲストでも試せる |
| 08 生成支援 | 参照素材、商品タイプ、スタイル、言葉の提案 | 初心者が空欄に困らない |
| 09 生成の期待値 | イメージ画像≠製造仕様と明記 | 誤認しないバッジ・注記 |
| 10 再生成・比較 | 好きでない結果を簡単に作り直せる | 生成前条件が保持される |
| 11 引用・系譜 | 親作品・作者・許諾を記録 | Remixでparent_idが残る |
| 12 発見と推薦 | 精度に加え新規性・多様性・改良可能性 | 同じテイストに固定しない |
| 13 アルゴリズム透明性 | なぜ表示されたかわかる | 「似た好み」「新しい発見」の表示を将来導入 |
| 14 社会的体験 | 強制的な交流より作品を媒介にした間接的共創 | 嫌がらせ・スパム対策が可能 |
| 15 支持表明 | 無料のお気に入り／条件付き購入意思を区別 | 金銭行動の意味が明確 |
| 16 価格実験 | 価格ごとの予約率、非購入を測る | 単なる寄付総額と混同しない |
| 17 商品化条件 | IP、品質、最低ロット、利益、需要 | 「人気でも商品化を保証しない」明記 |
| 18 報酬説明 | 現金契約とPICSY貢献度を分離 | 貢献度＝日本円という誤認を防ぐ |
| 19 信頼・権利 | 許諾範囲、二次創作、利用規約、審査 | 権利ステータスが監査可能 |
| 20 プライバシー | プロンプト利用、匿名化、データ保持期間 | 企画担当が生の個人データを閲覧しない設計 |
| 21 アクセシビリティ | キーボード・フォーカス・読み上げ・色・動き | WCAG 2.2 AAを目標に検証 |
| 22 レスポンシブ | 360pxスマホとデスクトップで同じ導線 | 生成・リミックス・予約が小画面で完遂 |
| 23 計測 | ファネル、コホート、作品分岐、価格実験 | イベント辞書が定義される |
| 24 失敗時UX | API失敗、権利不可、コスト上限、売切れ、未販売 | 元入力保持・安全な再試行・次の選択を提示 |

## 2. 具体的なUX設計手順（12工程）
1. **Research brief**：事業仮説と主要意思決定（創作需要、購買需要、改良率、採算）を文章化。
2. **現状行動観察**：高関与ファンが直近で買わなかったグッズを見せてもらう。推奨24〜30名は暫定値。
3. **JTBD / Opportunity mapping**：購入見送り、検索、SNSでの探索、創作、意思表明の未解決領域を可視化。
4. **セグメントと最初のジョブ選定**：初期は「好きだが欲しいデザインがない」ファンから開始。創作者と閲覧者を別ロールで設計。
5. **価値仮説と制約**：IP権利、製造仕様、円決済、PICSY未実装を明示。体験の誇大表示を防ぐ。
6. **ユーザーストーリー／情報アーキテクチャ**：発見→生成→改良→公開→購入希望を途切れなく接続。
7. **タスクフロー・画面遷移**：正常時だけでなく誤操作、生成失敗、権利不可、非購入を含める。
8. **低忠実度試作**：紙・ワイヤーフレームで「使ってみたい」が成立するかを早期確認。
9. **高忠実度UI＋デザインシステム**：タイポグラフィ、色、余白、カード、ダイアログ、空状態、アクセシビリティ。
10. **操作プロトタイプ・ユーザビリティテスト**：A/B/C体験を比較。中断箇所、独自の気づき、予約意思を見る。
11. **分析設計・価格検証**：イベント計測、ランダム化、価格提示条件、商品化の判断指標を確定。
12. **MVP実装・フィードバック**：バックログ優先順位、保守・運用、権利審査、次フェーズ移行基準を定める。

## 5. もう1つのジャーニー：閲覧専用のファン
ユーザーは生成せず商品一覧を探索する。カテゴリーで絞り、好みの作品を見つけたら購入意思を登録。生成しない人を離脱扱いにしない。創作参加率と購入関与率は独立して観測する。

## 6. デザインシステム（高忠実度プロトタイプの仕様）
**人格**：推し文化を尊重するが子どもっぽくない。体験は軽快・やわらかく、経営・分析機能は正確で静か。

- ブランド：「ゾクゾク」、約束：「好きがゾクゾクと。」。ユーザーへの命令より誘いを優先。
- パレット：メイン Purple `#7355DA`、文字 `#282438`、背景 `#FAF9FB`、カード `#FFFFFF`、ライン `#EBE8F0`。mintはサブ。
- 情報優先順位：作品ビジュアル ＞ 何ができるか ＞ 価格目安 ＞ 支持 ＞ 細かな説明。
- タイプ：日本語 Noto Sans JP（フォールバック system-ui）、英文 DM Sans。本文12〜14px、デスクトップ見出し24〜60px。
- 余白系：8px基準、ボタン高さ40〜50px、カード角丸16〜20px、主要コンテナ最大幅1570px。
- UI要素：商品カード、種類チップ、検索、スタイル、プロンプト、生成プレビュー、元作品リンク、支持ダイアログ、インサイトカード、空状態。
- アニメーション：ホバー移動2px程度、`prefers-reduced-motion`で停止。過剰なキラキラや点滅を避ける。
- コピー：「お気に入り」「リミックス」「この条件で購入意思を登録」。実決済しない画面で「購入完了」とは書かない。
- 状態：empty/loading/success/failure/no-results/no-rights/limited-stock/auth-neededを一覧化。MVPは主要な4状態を実装。
- 音声・補助：画像alt、画面見出し、フォーカスリング、キーボード、ARIAライブ通知、モーダルの操作を検証。
- モバイル：2列作品カード、縦一列生成フォーム、折り畳みメニュー、親指で押しやすいCTA。

## 7. おすすめアルゴリズムとオープンエンドネスの両立
好みに近いものだけを出すと探索が偏る。実装計画では、3つの推薦群を明確に分ける。

1. **Fit**：ユーザーの選択・改良・購入意思から、好みに近い候補を出す。
2. **Remixability**：ユーザーが改良したくなる、変化の余地がある作品を出す。
3. **Serendipity**：意図的に距離のあるデザインや支持の少ない新作を一定量入れる。

候補スコアの一例：`Score = 0.45 Fit + 0.30 Remixability + 0.25 Novelty`。数値は初期仮説であり、テストで検証する。高精度な学習モデルを初期条件にしない。最初は商品タイプ・スタイルタグ・新規性によるルールで十分。類似推薦で閉じないよう、実験では「新しく好きになった作品」と「実際の予約購入」を分けて測る。

## 8. ビジネスのUX：投票 ≠ 決済
UX上、4つを別概念にする。

| 操作 | 意味 | 金銭 | デモ実装 |
|---|---|---|---|
| お気に入り | 気になる（低コミット） | なし | 作品カードの支持人数は初期サンプル |
| 購入意思 | 表示条件なら買いたい | なし | 保存する模擬意思表示 |
| 商品化条件付き予約 | 特定条件なら購入・場合によって与信/前払 | 条件次第 | **未実装** |
| 購入 | 商品供給・注文契約の成立 | 実際の決済 | **未実装** |

本MVPは「欲しい！」のモーダルで*模擬購入意思を登録*するのみ。価格の支払意思額を推定するには、別途価格水準をランダム化したテストが必要。個人が出した自由な希望額の合計をそのまま需要曲線とみなさない。分析時は自己生成者と第三者を分ける。

## 9. 企業向けのインサイト設計
**目的**は「プロンプト件数」ではなく、売れる商品仮説を更新できること。分析画面は、入力情報→解釈→根拠→次の実験という経路を必須にする。KPIは①公開数②派生率③予約率④実購入率⑤価格別需要⑥在庫消化率⑦商品別限界利益⑧予測誤差。集計の分母、期間、ユーザー構成、自作/他作を区別する。個人プロンプトの直接公開を避け、匿名・集計したニーズのみを企画者へ提示する。

## 10. PICSYのUXと商品開発との接続
初期は3つのグラフ/台帳を分ける。
- **作品継承DAG**：`Artwork(id,parent_id,creator_id,reference_license,created_at)`。同一作品の派生を確実にたどれる。循環は不可。
- **評価ネットワーク**：`Evaluation(from,to,amount,source_event_id)`。引用＝評価増加を自動的に保証しない。仮想中央銀行法の`E'`を使うと`cE'=c`。
- **法定通貨の決済台帳**：`Order/Payment/Royalty`。法的義務や税・精算を扱いPICSY貢献度と混同しない。

PICSYに必要な価値設計は、取引が原作者に必ず利益を保証するわけではないこと、`sum(c)=N` という相対値であること、固定ロイヤリティ契約とは別であることを明示。先にシミュレーションによる設計検証を行う。

## 11. 実装アーキテクチャ：MVPと拡張設計
### 今回動くプロトタイプ
```text
Browser (HTML/CSS/ES Modules)
 ├─ state (items, works, reservations, generation)
 ├─ LocalStorage (デモの自作作品・疑似購入意思)
 └─ HTTP API
       ├─ GET  /api/status
       └─ POST /api/generate (prompt,kind,style)
             ├─ MOCK: template SVG (AIではないと明示)
             └─ AI:   server-side OpenAI Images API
                         OPENAI_API_KEY (never exposed to browser)
```
依存を少なくするため Node.js標準のHTTPサーバーで構築。初期画像は架空のオリジナル動物のみ。入力長・Origin・小規模レート制限・タイムアウト・エラー表示を実装。デモのAI生成ではリミックスの親作品IDを保存するが、画像編集（image-to-image）はまだ実装しない。API利用の条件・費用に応じて設定する。

### 商用MVP候補（別工程）
```text
React / Next.js frontend
   ├─ Guest / Auth + consent
   ├─ Explore & Create & Remix & Reservations
   └─ Admin insights
          │ HTTPS
Node.js / TypeScript API (auth, validation, quotas, audit)
   ├─ Generation Queue → provider adapters → object storage
   ├─ Artwork & Lineage → PostgreSQL
   ├─ Votes/Reservations → payments service
   ├─ License & Moderation → human review workflow
   ├─ Event Tracking → analytics warehouse
   └─ PICSY adapter → separate compute + ledger (future)
```
エンティティ：`User`, `IPLicense`, `Asset`, `Artwork`, `ArtworkVersion`, `RemixEdge`, `GenerationJob`, `PriceExperiment`, `PurchaseIntent`, `ProductCandidate`, `Product`, `Order`, `RoyaltyRule`, `EvaluationEvent`, `Company`, `AuditLog`。

**重要な非機能要件**：API鍵保護／認証・RBAC／データ最小化／IP許諾管理／ログの再現性／監査／レート制限／費用上限／画像ストレージ寿命／生成ジョブの冪等性／障害からの復旧／アクセス権／本番テレメトリー／利用規約／権利申立て手順／データ削除／サービス障害時の縮退運転。

**セキュリティの要点**：アカウントなしデモでは個人情報・カード情報を入力させない。商用では入力に不正な指示や個人情報が含まれることを前提として権限分離。出力のIP審査をモデル自身に丸投げしない。商品化を自動承認しない。ポイント・金銭・PICSYはイベント台帳を分ける。

## 12. API契約
`POST /api/generate` 例：
```json
{"prompt":"落ち着いた配色のオリジナル動物アクリルスタンド","kind":"acrylic","style":"minimal"}
```
応答：`{"mode":"demo|ai","image":"data:image/...","message":"..."}`。失敗時は`{"error":"..."}`とHTTP 4xx/5xx。`/api/status` は接続モードを返す。認証、画像編集、注文APIは含まない。

## 13. テスト計画とDefinition of Done
**単体**：プロンプト検証、デモ画像SVGエスケープ、ID整合、全カテゴリーの画像生成。**API**：ステータス・不正入力・生成上限・拒否・サーバー障害。**E2E（手動）**：探索→リミックス→生成→公開→模擬予約→マイ作品→インサイト。**アクセシビリティ**：キーボード、見出し順、ラベル、コントラスト、代替テキスト、モーダル焦点トラップ（本番前必須）。**レスポンシブ**：375/768/1440pxを検証。**リスク**：APIキー漏洩、無限生成、権利侵害、XSS、誤決済表示を優先。

完成の定義：①Node起動、②APIのデモ生成が成功、③作品のリミックス系譜が記録、④画像を公開して一覧に出る、⑤「欲しい！」から疑似予約できる、⑥費用がかかる実処理は鍵の有無で切り替わる、⑦未実装の決済・PICSYが明示される、⑧単体テストが通る。

## 14. Codexで継続開発するための段階的タスク
- **Task 1 (design system)**：色・タイポ・コンポーネント・アクセシビリティ仕様をレビュー。画面のレスポンシブを改善。
- **Task 2 (backend)**：SQLiteまたはPostgreSQL、認証、作品、リミックスDAG、権利ステータスを実装。
- **Task 3 (generation)**：画像編集APIを導入し、親画像の実際の改変・画像安全審査・生成ジョブ・料金制御を実装。
- **Task 4 (experiment)**：価格提示実験と購入意思ログをサーバー保存。非購入・離脱の計測。
- **Task 5 (commerce)**：許諾済み商品の試作・審査・実購入予約・在庫・注文・返金の統合。
- **Task 6 (PICSY simulator)**：作品系譜と取引関係から `E` を構築、仮想中央銀行法の再計算、固定ロイヤリティとの差異を試験。

## 15. 未実装・要検証（誤認防止）
- 実際の画像編集/複数案生成/AI推薦、実課金、IP検証、共同カンパニー、PICSY決済、リアルタイム多人数共有、在庫、製造注文は未実装。
- デモ画面の支持人数とインサイトは架空データ。購入意思も疑似値。顧客需要の実証には使えない。
- 「PICSYによって原作者へ必ず円が配られる」という設計にはしない。円建てロイヤリティは別。
- 会社の正式導入・許諾・実際の顧客調査結果を示すものではない。
